# ADR-0002: Write the daemon in Rust

- **Status:** Accepted
- **Date:** 2026-11-09

## Context

The legacy renderer is Python 3.7 on hzeller's Python bindings, running on a
**Pi Zero W: one ARMv6 core**. hzeller's library refreshes the panel from its
own thread. On multi-core Pis that thread gets a core to itself. On the Zero it
competes with everything else, so CPU spent in the application shows up as
flicker and refresh jitter. The interpreter, the GIL, and per-frame allocation
all cost cycles on that one core.

The goal is better performance. C++ and Rust were both acceptable. Rust was
preferred if it was viable.

## Decision

Write the daemon in Rust. Call hzeller's C++ driver through FFI (ADR-0004)
rather than reimplementing its timing-critical GPIO code.

## Consequences

- Native code with no interpreter or GC. A render loop that allocates nothing
  per frame and idles between changes (ADR-0006) leaves the core to the refresh
  thread.
- A single static binary of a few MB. No Python runtime and, later, no Node on a
  512 MB device.
- `cargo test`/`clippy`/`fmt` plus a strong type system give us the testing and
  hygiene the project wants.
- Viability is confirmed: the toolchain supports `arm-unknown-linux-gnueabihf`
  (ARMv6 hard-float), and the core already builds for it.
- Cost: cross-compiling, especially the C++ driver, adds build complexity
  (ADR-0007).
- **The gain has to be measured.** The refresh thread is C++ in both the old and
  new stack. Rust wins by taking less CPU *away* from it. We prove that with
  on-device numbers (ADR-0006), not assertions.

## Alternatives considered

- **C++.** Also viable, and the driver's native language. Rust was preferred,
  and it gives memory safety and a better test, lint, and dependency story at
  equal runtime cost.
- **Optimise the Python.** Doesn't remove the interpreter overhead on one core.
- **Go / other GC languages.** GC pauses and runtime footprint work against a
  single-core real-time panel.
